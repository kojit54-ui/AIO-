# RELEASE：公開と復旧の手順

## 環境

| 環境 | 用途 | DB | ブランチ |
|---|---|---|---|
| Preview | 作業ブランチの確認 | 検証用Supabase | 作業ブランチ |
| 本番 | 招待した顧客が利用 | 本番用Supabase | main |

- GitHubをVercelへ接続し、作業ブランチごとにPreviewを作る
- 検証と本番で、DB・APIキー・認証の戻り先URL・メール設定をすべて分ける
- mainへの統合が本番反映になるため、統合前にリリース判定を済ませる
- APIキーと管理用秘密キーはサーバーの環境変数だけに置き、ブラウザやGitに出さない

## リリースの完了条件

- [ ] 別企業のアカウントで、他社記事を読む・書くAPI操作が拒否される
- [ ] 再ログインすると下書きが戻る
- [ ] 生成失敗と二重実行を処理でき、入力が失われない
- [ ] 承認後に編集すると承認が無効になる
- [ ] 確認依頼が必須の会社で、未承認の記事を公開済みにできない
- [ ] HTML出力が検証対象社のブログ（種類ごとに1件以上）で崩れず、危険なコードを含まない
- [ ] PCとスマートフォンで主導線（テーマ選択から書き出しまで）が完了する
- [ ] 本番の招待メールが独自ドメインから届く
- [ ] 予算上限と通知が動く
- [ ] ログとエラー監視が動き、本文や個人情報をログに残していない
- [ ] 利用規約・プライバシー説明（AIへの送信範囲を含む）、問い合わせ窓口、削除手順が用意されている
- [ ] バックアップからの復旧を検証環境で一度試した

## 公開手順

1. リリース判定（上の完了条件）をタムさんが確認
2. DB変更は互換性を保つ形（列の追加を先に、削除は後の版で）で本番へ適用
3. mainへ統合し、本番デプロイを確認
4. 本番で招待から書き出しまで実操作で確認
5. URL、対象コミット、テスト結果を下の記録に追記

## 問題が起きたとき

- アプリはVercelで前のデプロイに戻す
- アプリを戻してもDBは戻らない。DBはバックアップからの復旧で対応する（手順はT3-5で記入）
