# LESSONS：経験から決めたルールと用語集

不具合・レビュー指摘・本番の確認・利用者の声で分かったことを、次の作業で守るルールとして残す。CC・CX のどちらも作業前に目を通す。

考え方の出典：2026-10-23 共有の講演資料「印刷業界におけるAI活用」（Fam-Time 西村威彦氏）。AIは優秀だが自社の前提を知らない新人と同じ。経験を手順・ルール・テストに書き残す仕組み（ハーネス）が、モデルの違い以上に成果を左右する。

## 進め方

- 人（タム）が決めるのは、目的、任せる範囲、リリースしてよいか。要求整理から実装・テスト・手直しまでは CC・CX が進め、もう一方がレビューする
- コードを変えるときは、テストも追加・更新する。コードの不具合を直したら、同じ不具合を検出するテストも足す。文書や手順だけの変更ではテストは不要
- 分からない前提は推測で埋めない。docs/ を確認し、それでも無ければ「未確認」と書いてタムさんに聞く。動作や仕様は、実際に動かして確かめてから「できた」と書く
- 検証用（Supabase の検証プロジェクト、Vercel のプレビュー）と本番を分け、本番への変更はタムさんの承認後に行う

## ルールを足すとき

1. 問題が起きたら、原因と再発防止策を整理する
2. 下の表に「ルール」と「なぜ」を1行で足す。仕様が変わる場合は docs/DECISIONS.md にも書く
3. 必要ならテストやチェックも足す。PRでタムさんが承認したら確定
4. ver1 リリース後は、利用者の声・障害・遅さからも同じ手順でルールを足す

## 用語集

画面・コード・docs で同じ言葉を使う。新しい言葉を作ったらここに足す。

| 用語 | 意味 |
|---|---|
| タム／CC／CX | 田村巧次さん（決める人）／Claude Code（画面）／Codex（認証・DB・AI接続・テスト・公開設定） |
| AIO | AI（Google の AI による概要、ChatGPT など）に、答えの中で会社や記事を紹介してもらうための工夫。目的は AI時代にウェブサイトで売上を上げること。docs/AIO.md |
| AIOの知識表／しおりのAIOニュース | AI検索の最新情報を1件ずつ持つ表（src/lib/aioNews.ts）／それを顧客のホームで伝えるカード |
| AIに選ばれる／お客様に選ばれる | このサービスの2つの段階。AIに選ばれる＝AIの答えの中で紹介されること。お客様に選ばれる＝紹介されて読みに来た見込み客（これから出会うお客様）が「ここに頼みたい」と思い、問い合わせること（いちばん大切）。画面の短い札は「お客様に選ばれる」、ひとことは「これから出会うお客様に選ばれる」。AIへの指示では「お客様」が記事を書く会社の人を指すことがあるので「見込み客」と書く。見出しや呼びかけでは「選ばれる」、仕組みの説明では「紹介される」を使ってよい |
| 伴走 | しおり（AI）が、最初の質問から記事・チェック・ブログに載せたあとまで、となりで案内し続けること |
| サービスの名前 | 画面では「コタムのブログ執筆支援」にそろえる（src/lib/brand.ts の SERVICE_NAME）。案内役は「しおり」、ひとことは「AIに選ばれて、これから出会うお客様に選ばれる会社へ。」 |
| 表記 | 顧客の会社のお客は「お客様」、「いっしょに」はひらがな、チェックは「AIOのチェック」（スタンプなど短い札だけ「AIOチェック」でよい） |
| AIOの材料 | AIが紹介しやすい記事に入っているもの。体験・数字・誰が/どこで・質問と答え・比べる材料・プロの知見・次の一歩・気持ちと想い・信頼の9つ |
| 顧客担当者（client_member） | コタムの既存顧客の会社で記事を書く人 |
| コタム担当者（coach） | 顧客を月1回指導し、記事を確認する人 |
| 全社管理者（admin） | 全社の管理と招待をする人 |
| 顧客向けの言い方 | ヒアリング→「会社のことを教える」、記事の設計図→「書く記事を決める」（提案は「おすすめ」「記事のセット」）、キーワード管理表→「書く記事リスト」、柱の記事（ピラー）→「まとめ記事」、周りの記事（クラスター）→「くわしい記事」、柱ごと→「テーマごと」、優先度→「おすすめ度」、公開済み→「やった」、月間検索数→「月の検索回数」、読む人が知りたいこと→「お客様が知りたいこと」。記事の画面では、見出し案→「見出し」、第N版→「N回目の保存」、版の履歴→「前の内容に戻す」、確認依頼→「コタムに見てもらう」、承認→「コタムのOK」、公開済みにする→「ブログに載せた」、要確認→「確かめる」、指導方針→「今月の方針」、会社プロフィール→「会社の情報」、作風→「画像の雰囲気」。記事の状態は 書いている／コタムが確認中／直してほしい所あり／コタムのOK／ブログに載せた。コードと docs の中は今までの言葉のままでよい |
| 指導メモ | コタム担当者が月ごとに書く方針。顧客向けメモはAIに渡し、内部メモは顧客にもAIにも渡さない |
| 確認済みプロフィール | 顧客が内容を確認した会社情報。AIに渡すのはこれだけ |
| 要確認箇所 | 数値・実績・価格・顧客名など、本文の中で事実を確かめるべき箇所 |
| 確認依頼 | 顧客がコタム担当者に記事の確認を頼むこと。必須か任意かは会社ごと |
| 版 | 記事の保存ごとの履歴。承認は確認依頼した版に対して行う |
| 生成上限 | 本文の生成回数の上限（1社月30回、1記事10回）と全社の月額予算 |
| サンプル（AIは未接続） | APIキーが無いときに返す見本。本物のAIの結果に見せない |
| 検証用／本番 | 架空データで試す環境／実際の顧客が使う環境。DB と秘密情報を分ける |
| 書き手／点検役／画像の提案役 | AIの役割。書き手（OpenAI）が見出し案・本文を書き、点検役（Anthropic）の指摘で1回書き直す。画像の提案役（Google）がアイキャッチと見出しごとの画像を考える |
| AIの点検 | 点検役が、独自性・AI検索への対策・AIが書いたように見えないか・事実・文体を確かめた結果。記事の画面の「AIの点検」タブに出る |
