# LESSONS：経験から決めたルールと用語集

不具合・レビュー指摘・本番の確認・利用者の声で分かったことを、次の作業で守るルールとして残す。CC・CX のどちらも作業前に目を通す。

考え方の出典：2026-10-23 共有の講演資料「印刷業界におけるAI活用」（Fam-Time 西村威彦氏）。AIは優秀だが自社の前提を知らない新人と同じ。経験を手順・ルール・テストに書き残す仕組み（ハーネス）が、モデルの違い以上に成果を左右する。

## 進め方

- 人（タム）が決めるのは、目的、任せる範囲、リリースしてよいか。要求整理から実装・テスト・手直しまでは CC・CX が進め、もう一方がレビューする
- コードを変えるときは、テストも追加・更新する。コードの不具合を直したら、同じ不具合を検出するテストも足す。文書や手順だけの変更ではテストは不要
- 分からない前提は推測で埋めない。docs/ を確認し、それでも無ければ「未確認」と書いてタムさんに聞く。動作や仕様は、実際に動かして確かめてから「できた」と書く
- 検証用（Supabase の検証プロジェクト、Vercel のプレビュー）と本番を分け、本番への変更はタムさんの承認後に行う

## ルールを足すとき

1. 問題が起きたら、原因と再発防止策を整理する
2. 下の表に「ルール」と「なぜ」を1行で足す。仕様が変わる場合は docs/DECISIONS.md にも書く
3. 必要ならテストやチェックも足す。PRでタムさんが承認したら確定
4. ver1 リリース後は、利用者の声・障害・遅さからも同じ手順でルールを足す

## 用語集

画面・コード・docs で同じ言葉を使う。新しい言葉を作ったらここに足す。

| 用語 | 意味 |
|---|---|
| タム／CC／CX | 田村巧次さん（決める人）／Claude Code（画面）／Codex（認証・DB・AI接続・テスト・公開設定） |
| 顧客担当者（client_member） | コタムの既存顧客の会社で記事を書く人 |
| コタム担当者（coach） | 顧客を月1回指導し、記事を確認する人 |
| 全社管理者（admin） | 全社の管理と招待をする人 |
| 指導メモ | コタム担当者が月ごとに書く方針。顧客向けメモはAIに渡し、内部メモは顧客にもAIにも渡さない |
| 確認済みプロフィール | 顧客が内容を確認した会社情報。AIに渡すのはこれだけ |
| 要確認箇所 | 数値・実績・価格・顧客名など、本文の中で事実を確かめるべき箇所 |
| 確認依頼 | 顧客がコタム担当者に記事の確認を頼むこと。必須か任意かは会社ごと |
| 版 | 記事の保存ごとの履歴。承認は確認依頼した版に対して行う |
| 生成上限 | 本文の生成回数の上限（1社月30回、1記事10回）と全社の月額予算 |
| サンプル（AIは未接続） | APIキーが無いときに返す見本。本物のAIの結果に見せない |
| 検証用／本番 | 架空データで試す環境／実際の顧客が使う環境。DB と秘密情報を分ける |
